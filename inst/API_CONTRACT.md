# bwTools public API contract

Version: **schema 2 / bwTools 0.8.6**

Version 0.8.0 is the downstream-integration stability baseline. Packages such
as GeneTrackR should depend on the public functions and schemas documented here
rather than private `bwTools:::` implementation details.

Version 0.8.6 preserves the same public contract. Documentation is reorganized
into focused vignettes and all exported functions receive standardized examples
and return documentation. The optional external compatibility harness and the
0.8.5 multi-sample behavior remain unchanged, with no public signature or
BwgTrack schema v2 changes.

## Stable public API

```{text}
detect_bwg_format()
read_bwg()
bwg_track()
validate_bwg()
is_bwg_track()
samples_bwg()
seqinfo_bwg()
metadata_bwg()
zoominfo_bwg()
retrieve_bwg()
merge_bwg()
stats_bwg()
summary_bwg()
write_bwg()
benchmark_bwg()
```

Normal analysis functions consume a validated `BwgTrack`. Signal file paths
enter through `read_bwg()` and signal files leave through `write_bwg()`.
`benchmark_bwg()` is the only diagnostic exception because its purpose is to
measure file-I/O behavior directly.

Public function parameter names and order are regression-tested from 0.8.0.
Intentional future breaking changes must be documented explicitly in NEWS and
accompanied by a major compatibility decision before downstream integration is
updated.

## Standard argument vocabulary

```{text}
files       one or more signal paths passed to read_bwg()
file        one BigWig path passed to benchmark_bwg()
x           one BwgTrack object
sample_ids  sample identifiers or sample selection
samples     sample metadata used by bwg_track()
regions     genomic interval table
chrom       chromosome name
start       1-based closed start coordinate
end         1-based closed end coordinate
outdir      output directory used only by write_bwg()
```

Selector arguments named `sample_names` or `samples` are not part of the
standardized API. Enumerated character arguments use exact documented values;
partial matching is not part of the stability contract.

## BwgTrack schema v2

```{text}
BwgTrack
├── samples: sample_id, file, format, strand, has_strand
├── data: sample_id, chrom, start, end, value, strand OR NULL for lazy mode
├── seqinfo: sample_id, chrom, length
└── meta: coordinate, schema_version, backend, mode
```

In-memory coordinates are always 1-based closed.

Core field types after `bwg_track()` normalization:

```{text}
sample_id, file, format, strand, chrom  character
has_strand                            logical
start, end, length                    integer
value                                 numeric
```

Required metadata:

```{text}
coordinate     "1-based closed"
schema_version "2"
backend        non-empty character scalar
mode           "memory" or "lazy"
```

Lazy schema-v2 tracks are backed by existing local BigWig files. Memory tracks
contain standardized signal data.

## Stable accessor and result schemas

`samples_bwg()` core columns:

```{text}
sample_id  file  format  strand  has_strand
```

`seqinfo_bwg()` core columns:

```{text}
sample_id  chrom  length
```

`retrieve_bwg(..., result = "data")` core columns:

```{text}
sample_id  chrom  start  end  value  strand
```

Strand selection is exact. Lazy BigWig-backed samples use sample/file-level
strand metadata. Memory-mode tracks use row-level `data$strand`, so a sample
whose sample-level metadata is `"*"` can still be queried for `+` or `-` when
its signal table contains those strands. `result = "track"` normalizes the
returned selected sample metadata to the requested exact strand.

`stats_bwg()` core columns:

```{text}
sample_id  chrom  start  end  stat  value  covered_bases  source  resolution
```

Fully out-of-range `retrieve_bwg()` and `stats_bwg()` calls retain these core
columns with zero rows rather than returning a zero-column data.table.

`zoominfo_bwg()` core columns:

```{text}
sample_id  level  data_offset  index_offset
```

`summary_bwg()` columns:

```{text}
samples  mode  intervals  chromosomes  coordinate  schema_version  backend
```

`write_bwg()` returns an invisible manifest with:

```{text}
sample_id  file  format
```

For memory-mode objects, every selected sample must contain at least one signal
record. Validation occurs before any selected sample is written so the manifest
cannot silently omit an empty selected sample while leaving partial files.

Downstream packages should use public accessors instead of direct assumptions
about internal object implementation. `metadata_bwg()` is the public metadata
accessor for schema, operation, and provenance fields.

## Error contract

Errors intentionally generated by bwTools public validation and I/O checks
inherit from:

```{text}
bwTools_error
```

Downstream packages may therefore use:

```{r}
tryCatch(
  bwTools_call(),
  bwTools_error = function(e) conditionMessage(e)
)
```

Human-readable error messages may be improved over time. Downstream control
flow should prefer the condition class rather than exact full-message matching.
Errors originating directly from the operating system or an external R package
may retain their native condition classes.

## Coordinate contract

Public R objects:

```{text}
1-based closed
```

BigWig and bedGraph on disk:

```{text}
0-based half-open
```

All file readers and writers perform the conversion at the I/O boundary. Query
coordinates passed to `retrieve_bwg()` and `stats_bwg()` are always 1-based
closed positive integer coordinates.

The schema-v2 in-memory coordinate fields `start`, `end`, and known `length`
values remain R integer columns and therefore support coordinates through
`.Machine$integer.max`. BigWig chromosome lengths larger than that can be parsed
internally from the file but are represented as `NA` in public `seqinfo`, and
full-resolution coordinates beyond the R integer range are not materialized.

When selected samples provide known chromosome lengths in `seqinfo`:

```{text}
unknown chromosome             -> bwTools_error
end beyond chromosome length   -> clip to chromosome length
start beyond chromosome length -> typed empty result
conflicting known chromosome lengths -> bwTools_error
```

`stats_bwg()` applies chromosome-end clipping before bin construction, so memory
and lazy BigWig modes use the same effective interval. If the clipped interval
contains fewer bases than `n_bins`, normal bin-count validation raises an error.

A selected sample is considered to have complete sequence metadata only when
all of its `seqinfo$length` values are known. WIG and bedGraph inputs do not
carry chromosome lengths. Their automatically constructed `seqinfo` rows
therefore use `length = NA`; absence of another chromosome from such incomplete
metadata is interpreted as no observed signal rather than proof that the
chromosome is invalid.

If `seqinfo` is supplied for a memory-mode track, every signal
sample/chromosome pair must occur in `seqinfo`, and signal ends may not exceed a
known chromosome length.

## Merge contract

`merge_bwg()` is the only public merge interface.

```{text}
method = "auto"  conservative non-arithmetic merge
method = "mean"  explicit arithmetic mean
method = "sum"   explicit arithmetic sum
```

Automatic merging never averages or sums different sample IDs merely because
coordinates overlap. Conflicting same-sample overlaps require an explicit
arithmetic method.

## Write contract

Only `write_bwg()` persists signal files. Retrieval, merging, and statistics do
not write files.

Supported output formats:

```{text}
bigwig
wig
bedgraph
```

WIG and bedGraph may be gzip-compressed. BigWig output may include the native
zoom pyramid. `max_zoom_levels = 0L` is valid and disables zoom records even
when `zoom = TRUE`.

## Cross-format stability

The 0.8.0 regression suite checks that standardized full-resolution signal is
preserved across:

```{text}
BwgTrack → BigWig without zoom → BwgTrack
BwgTrack → BigWig with zoom    → BwgTrack
BwgTrack → WIG                 → BwgTrack
BwgTrack → WIG.gz              → BwgTrack
BwgTrack → bedGraph            → BwgTrack
BwgTrack → bedGraph.gz         → BwgTrack
```

BigWig zoom metadata may differ according to writer options; full-resolution
signal must not.

Starting with 0.8.4, an optional installed compatibility harness can validate
BigWig interoperability against independent implementations when they are
available:

```{text}
pyBigWig / libBigWig
rtracklayer
UCSC BigWig utilities
```

These implementations are development references only. They are not runtime
dependencies and are not part of the 15-function public API. Compatibility is
judged by chromosome lengths, missing-signal positions, and signal values rather
than byte-identical files or identical internal block segmentation. See
`inst/COMPATIBILITY.md`.

## Benchmark contract

`benchmark_bwg()` returns:

```{text}
bwToolsBenchmark
├── system
├── file
├── config
├── regions
├── results
└── summary
```

Benchmarking is an advanced diagnostic feature and is not required for normal
downstream integration. It does not alter the BwgTrack schema or write a
persistent benchmark report automatically.

Peak-memory metrics are approximate R heap high-water measurements from `gc()`
rather than process RSS. Metadata-cold runs do not clear the operating-system
file cache.
